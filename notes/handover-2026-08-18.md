# Handover — Discogs build on the droplet, 2026-08-18

Written for whoever picks this up next, most likely an agent running **on the
droplet itself** rather than in a sandbox. It covers the debugging that started
once the pipeline first ran against real data, and what to do next.

Repo state at handover: branch `claude/extract-archive-update-docs-c14mck`,
head `422fd5a`. Everything described below is committed and pushed.

---

## 1. Where things stand

The transform has **succeeded**. The import has **not**. Nothing is lost.

On the droplet, under `/var/lib/music-graph/data`:

| | |
|---|---|
| `discogs_20260801_*.xml.gz` | all four dumps, downloaded and sha256-verified |
| `*.xml.gz.ok` | sentinels; their presence makes re-runs skip the download |
| `labels.db` | SQLite labels staging table, 2,405,206 rows — **pre-fix, no sublabels** |
| `csv/*.csv` | the eight import CSVs — **pre-fix, wrong ID-space headers** |
| `csv/import.report` | bad rows from the failed import |

Neo4j's store is in the "likely unusable" state the importer warns about after
aborting. That is fine: `neo4j_admin_import.sh` passes `--overwrite-destination`,
so a re-import replaces it wholesale. Do not try to repair it.

The viewer service is already running — provisioning deliberately installs it
*before* the slow steps so `/logs` is watchable during a build. It will report
"graph not loaded yet" until an import lands.

Measured figures from the successful transform, worth keeping for comparison:

```
labels      2,713,531 elements   2m 11s      (2,405,206 top-level + ~308k sublabel refs)
artists    10,163,318 elements   6m 56s
masters     2,579,897 elements   2m 06s      -> 2,579,897 distinct main_release ids
releases   19,341,287 scanned   58m 50s      -> 2,579,769 written (128 ids absent from the dump)
```

Roughly 4,800–5,500 releases/s, one core, ~1 hour for the releases pass. The
transform is single-threaded by design and cannot easily be parallelised: gzip
is a serial stream, so splitting it means decompressing ~110 GB to disk, which
is the whole thing the prefilter route exists to avoid. Measured split is ~13%
inflate, ~87% lxml parsing, so moving inflate to a second core buys about 9%.

## 2. Do this next

The last failure was a modelling bug whose fix is **header-only** for three of
the CSVs, so the 59-minute releases pass does not need repeating.

```bash
# Pin the branch explicitly. provision_droplet.sh used to default REPO_BRANCH
# to main and `checkout` + `reset --hard` onto it, so an earlier run may have
# left this checkout on main with none of the fixes. See 3.5.
cd /opt/music-graph
git fetch origin claude/extract-archive-update-docs-c14mck
git checkout claude/extract-archive-update-docs-c14mck
git pull
D=/var/lib/music-graph/data

# 1. repoint the artist/group ID space. The trailing \r matters: csv.writer
#    emits CRLF, and these edits must not break that convention.
sed -i '1s|.*|"artistId:ID(Entity)","name","realname","profile"\r|' $D/csv/artists.csv
sed -i '1s|.*|"groupId:ID(Entity)","name","profile"\r|'             $D/csv/groups.csv
sed -i '1s|.*|":START_ID(Entity)",":END_ID(Entity)"\r|'             $D/csv/artist_group_links.csv
sed -i '1s|.*|":START_ID(Entity)",":END_ID(Release)"\r|'            $D/csv/artist_release_links.csv

# 2. register sublabels as Label nodes, then re-export labels.csv (~2 min)
rm -rf /tmp/relabel && mkdir -p /tmp/relabel
python3 discogs_to_neo4j.py --label-xml $D/discogs_20260801_labels.xml.gz \
    --label-sqlite $D/labels.db --output-folder /tmp/relabel
python3 sqlite_to_csv.py --sqlite-path $D/labels.db --output-folder $D/csv

# 3. re-import; download and transform are skipped automatically
export DUMP_DATE=20260801
export NEO4J_PASSWORD=...        # see /etc/music-graph.env
export APP_PASSWORD=...
./provision_droplet.sh
```

Those `sed` commands were verified byte-for-byte against what the fixed
transform emits, CRLF included.

This leaves two records missing as nodes — artist `66827` and label `212`, both
of which lack a `<name>` and were dropped by the old code. Two rows against a
50,000 tolerance is immaterial. If you want a fully clean build instead, delete
`$D/csv/*.csv` and `$D/labels.db` and let the transform run from scratch (~70
minutes); the dumps are still there so nothing re-downloads.

## 3. What went wrong, in order

Four failures, each with a fix that is committed. Read this before diagnosing
anything new — several of them look like something they are not.

### 3.1 HTTP 403 on every dump URL — `234331d`

The S3 bucket does not serve objects to anonymous callers, so direct GETs 403.
Worse, the bucket also denies anonymous *listing*, which makes S3 answer **403
rather than 404** for a key that is simply absent — so a wrong path is
indistinguishable from refused access. Downloads now go through the Discogs
front end, which takes the key url-encoded in a query parameter:

```
https://data.discogs.com/?download=data%2F2026%2Fdiscogs_20260801_artists.xml.gz
```

`dump_url()` builds this; `DUMP_HOST` and `DUMP_PREFIX` override it. Preflight
now HEADs all four URLs so a bad date fails in seconds. **It must be HEAD** — a
server that ignores `Range` answers a ranged GET with the entire body, which
during a "quick check" would pull 10 GB.

### 3.2 Download died at 2.1 GB of 10.4 — `7215846`, `c1edbef`

`curl: (92) INTERNAL_ERROR` — a Cloudflare HTTP/2 stream reset, routine on
multi-GB transfers. Three faults combined:

- HTTP/2 itself.
- `--retry` never fired: curl does not retry protocol errors without
  `--retry-all-errors`.
- The error path deleted the partial, discarding 2.1 GB that `-C -` could have
  resumed.

The first fix (curl with `--http1.1 --retry-all-errors`) was **wrong in a way
worth remembering**: measured against a server that severs the connection and
logs `Range` headers, curl's internal retry restarts from byte 0 every time —
four retries, four `Range=(none)`. On a 10 GB file that converts one abort into
several full re-downloads. wget under the identical test resumes properly
(`0 → 3285 → 5475 → 6935 → 7908`), and wget 1.x has no HTTP/2 at all, so the
reset cannot recur rather than merely being configured away.

**Dumps are fetched with wget. Do not switch back to curl for them.**

### 3.3 `AccessDeniedException: /import.report` — `a3c1f1a`

Not a permissions problem in any interesting sense. `neo4j-admin` writes its
bad-rows report to `import.report` **relative to the current directory**;
provisioning runs from `/` because that is cloud-init's cwd and `sudo -u` does
not change it, so the unprivileged `neo4j` user was trying to write to the
filesystem root. Now passed explicitly via `--report-file`, with a `cd` as well.

### 3.4 Import aborted on 250,004 bad relationships — `422fd5a`

**The tolerance was right and the model was wrong.** Do not raise
`--bad-tolerance` to get past this class of failure.

Discogs issues artist and group IDs from one sequence, and a release credits a
band with exactly the same kind of ID it uses for a person — `process_release`
cannot tell which it has. Artists and groups were written into *separate*
import ID spaces, so every release credited to a band produced a dangling
`CREDITED` row: the band's id lives in `groups.csv` while the edge declared
`:START_ID(Artist)`. Across 13.9M CREDITED rows that is millions of dangling
edges; 250,004 is merely where the importer stopped counting.

Artists and groups now share one space, `Entity`. It stays unique because each
Discogs id lands in exactly one of the two files.

Two smaller sources of dangling edges were fixed in the same commit:

- Sublabels were written as relationship endpoints but never as `Label` nodes.
- A record with no `<name>` raised past its handler and was dropped whole (one
  artist, one label in this dump), while its id stayed referenced elsewhere.

### 3.5 The provisioning script checked out `main` over the working branch

`REPO_BRANCH` defaulted to `main`, and `fetch_repo` does `checkout` followed by
`reset --hard`. Running the script by hand without exporting `REPO_BRANCH` --
which is exactly what the recovery instructions said to do -- therefore moved
`/opt/music-graph` onto `main`, silently discarding every fix, and then carried
on running the code it had just replaced.

It only stayed hidden because `cloud-init.example.sh` exports `REPO_BRANCH`, so
the unattended first boot was always correct.

`REPO_BRANCH` now defaults to whatever branch the checkout is already on,
falling back to `main` only when there is no checkout to read (a first clone).
Switching branches is still possible by exporting `REPO_BRANCH`, but the script
now says on stderr when it is about to do so. Verified against a real
two-branch repo: without the variable the feature branch survives, with it the
override still works, and a missing checkout still resolves to `main`.

**If a checkout is on the wrong branch, check the file contents, not just the
branch name** -- a `reset --hard` will have taken the working tree with it.

## 4. Things that look like bugs but are not

- **`open_writer` opens CSVs in append mode.** Re-running the transform into a
  non-empty folder duplicates every row. The transform therefore *refuses* to
  start if the output folder holds any `.csv`. That refusal is deliberate;
  switching to `"w"` would clobber output on partial re-runs.
- **CSVs are CRLF.** `csv.writer` defaults to `lineterminator='\r\n'`. Any
  hand-editing must preserve it.
- **`artists.csv` has more lines than artists** (10,481,018 vs 10,163,318).
  Profile text contains newlines inside quoted fields, which is why the import
  needs `--multiline-fields=true`.
- **`labels.csv` is written twice.** The transform leaves a header-only
  placeholder; `sqlite_to_csv.py` overwrites it with the real export. Skipping
  that second step yields an empty label set.
- **The `[label] done: 2,713,531` count exceeds `labels.csv`'s 2,405,206 rows.**
  The difference (~308k) is sublabel references, which are nested `<label>`
  elements inside `<sublabels>`.
- **128 `main_release` ids were not found in the releases dump.** 0.005%, just
  Discogs referential drift. Not a bug; no edges reference them, because links
  are only written for releases that were found.
- **The transform pegs one core (25% on 4 vCPU).** Expected — see §1. The other
  cores are used by `neo4j-admin import` and the index build.

## 5. What good looks like

The import fails fast — the last one aborted 1m 2s in, at the relationship
stage — so you get feedback quickly rather than after half an hour.

After a successful run:

```bash
python3 graph_stats.py            # node/rel counts, step timings, disk
python3 graph_stats.py --deep     # hubs, unconnected nodes, releases by decade
cat /var/log/music-graph.report.txt
```

Expected shape, from the CSV row counts already on disk:

| | |
|---|---|
| Artist + Group | 10,163,318 combined (minus the 1 dropped record) |
| Release | 2,579,769 |
| Label | ~2.4M, plus sublabels once §2 step 2 has run |
| MEMBER_OF | 2,367,235 |
| CREDITED | 13,926,485 |
| RELEASED_ON | 3,003,936 |
| SUBLABEL | 308,335 |

If `SUBLABEL` comes back near zero, step 2 of §2 did not take. If `CREDITED` is
far below 13.9M, the ID space is wrong again.

`import.report` should be empty or near-empty. If it is not, read it — it names
the offending rows, and it is now written somewhere writable.

## 6. Environment notes

- Credentials live in `/etc/music-graph.env`, mode 600. They are also in the
  originating chat, so treat them as throwaway and rotate if the droplet
  outlives the experiment.
- Neo4j is Community Edition, which serves exactly **one** user database. The
  import targets `neo4j`; naming it anything else yields a database Neo4j will
  not start.
- Neo4j binds localhost. `ufw` allows only 22 and the app port, so 7474/7687
  are unreachable from outside even if the Neo4j config changes.
- The viewer is plain HTTP with basic auth, so its password crosses the wire in
  the clear. Fine for a throwaway droplet; put it behind TLS before anything else.
- `provision_droplet.sh` is idempotent throughout, and re-execs itself if a
  `git pull` rewrites it mid-run (bash reads scripts incrementally by byte
  offset, so that would otherwise corrupt the run).
- Progress goes to `/var/log/music-graph.{log,status,steps.jsonl}` and is served
  at `/logs`.

## 7. Known loose ends

- Artist `66827` and label `212` are missing as nodes unless the transform is
  re-run from scratch. Immaterial at this scale.
- The `--deep` queries in `graph_stats.py` have never run against a populated
  graph of this size. They scan, and are individually fault-tolerant, but their
  runtime is unmeasured. Try them once the import lands.
- Nothing in this project has been tested against a second month's dump. The
  first re-run is where the `DUMP_DATE`/`DUMP_PREFIX` plumbing gets exercised.
