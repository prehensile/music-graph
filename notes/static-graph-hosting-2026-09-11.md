# Static-hosting the whole graph (not just search), 2026-09-11

Exploratory only — nothing implemented. Scopes the next step past
`notes/static-search-downsize-2026-08-19.md`: that note (and
`shard_search_index.py`) got *search* to a backend-free static index. This
note is about the other half — tap-to-expand, currently `/api/expand` —
going static too, so `server.py`/Neo4j can be dropped from serving
entirely and the viewer becomes pure static files plus a graph-rendering
JS lib in the browser.

## The question, and the framing that answers it

> Export all nodes to JSON files, including their edges, and reconstruct
> the graph client-side.

Taken completely literally — one JSON file per node — this doesn't work,
for reasons that have nothing to do with JSON or graph theory and
everything to do with how filesystems and static hosts behave at millions
of small files. That's the first thing to settle, because it decides the
shape of everything downstream.

## Millions of files: yes, this is a real problem

At current scale (15.16M nodes post "Not On Label" cleanup, ~19.6M
relationships summed across `MEMBER_OF`/`CREDITED`/`RELEASED_ON`/
`SUBLABEL`/`ALIAS_OF` — see CLAUDE.md's Data Model and Known Issues
sections), one file per node means ~15M files. Concretely, at that count:

- **Small-file overhead dominates.** Most filesystems allocate in
  whole blocks (ext4 default 4 KiB). A node's own record — id, type,
  name, a capped neighbour list — compacts to a few hundred bytes, the
  same order as one row of `search_index_export.csv.gz` (that export
  averaged ~36 bytes/row uncompressed for *just* `type,id,name,degree`;
  edges add more). Rounding every one of 15M such records up to a full
  block wastes several GB in pure slack space before counting the actual
  data — the same shape of problem `notes/static-search-downsize-2026-08-19.md`
  hit with the naive one-row-per-file idea, just now for every node
  instead of every search term.
- **inodes, not just disk space, can run out.** `df` reporting free space
  says nothing about free inodes (`df -i`); a filesystem or container
  overlay provisioned with a smaller-than-assumed inode ratio can refuse
  new files while gigabytes of space remain free. Worth checking with
  `df -i` on whatever box would hold the export, but the safer move is
  not needing 15M inodes for this in the first place.
- **A single flat directory with millions of entries is pathological**
  for anything that lists it — `ls`, `tar`, `rsync`, `find`, backup tools
  — even with ext4's htree directory indexing, which speeds up single-name
  lookups but not bulk enumeration. Nesting into subdirectories only
  delays the problem to whichever level still ends up with hundreds of
  thousands of entries.
- **git cannot hold this.** If the export is meant to live in this repo
  (or any git-backed static host) the way `web/vendor/` or `web/` does,
  committing 15M files makes `git status`/`git add`/`git diff` and
  packfile generation impractically slow, independent of the filesystem
  underneath — git's own object model, not ext4, becomes the bottleneck.
  (`web/search-index/` from the sharding work sidesteps this the same
  way proposed below: it's a build output, generated by
  `shard_search_index.py` on whatever box runs it, and isn't present or
  tracked in this checkout — `.gitignore` doesn't even need an entry for
  it because nothing has committed it yet. Worth adding one deliberately
  once a graph-shard directory exists too, rather than relying on nobody
  having run `git add -A` in that directory by accident.)
- **Static hosts cap files per deploy.** This is the sharpest practical
  wall: Cloudflare Pages limits a deployment to 20,000 files; other hosts
  are more generous but still degrade badly well before 15M (per-deploy
  diffing and upload go file-by-file). A plan that produces 15M files
  can't be deployed to most static hosts at all, independent of whether
  the filesystem building it would even finish.

None of this is specific to Linux or ext4 — it's the general shape of
"many small files" problems, and it's exactly what
`shard_search_index.py` was already built to dodge for the search index.
**The fix carries over directly: don't emit one file per node. Shard.**

## The shape that fits: id-hashed shards, same two-phase build

`shard_search_index.py` shards by **text prefix**, because search is
"what does the user's partial typing resolve to." Expand is a different
access pattern — "given one specific node id, what are its edges" — so
the shard key has to be the **id**, not a prefix. Concretely:

1. **Bucket nodes by a hash of `(type, id)` into a fixed number of shard
   files** (thousands, not millions — see sizing below), each holding a
   JSON array of many nodes' records. A node's shard is `hash(type, id)
   % N`, computable identically in the Python build and the JS client, so
   — same as the search shards — **no manifest is needed**: the client
   computes the shard filename directly from the id it already has (the
   one it's expanding) and fetches it.
2. **Use a hash function trivial to reimplement byte-identically in both
   Python and JS**, not `blake2b` (what `shard_search_index.py` uses
   server-side only, never client-side, so it never had to cross the
   language boundary). FNV-1a is the standard choice here: a dozen lines,
   no library, unambiguous over integers. `partition_key`'s use of
   `hash()` would be *wrong* to reuse client-side even in Python-to-Python
   terms — it's explicitly salted per-process — so this needs a new,
   deliberately portable function regardless.
3. **Two-phase build, same reason as before**: flat peak memory
   regardless of the 15M-node input, proven necessary already on the
   downsized `s-2vcpu-4gb` droplet (3.8 GiB total, ~1.2 GiB available at
   the time `shard_search_index.py` was built). Phase 1 partitions node+edge
   rows into N scratch buckets by the same hash used for final sharding
   (so phase 2 never needs to re-shuffle across files); phase 2 loads each
   bucket, assembles the final per-node record, and writes it out.
4. **Recursion isn't needed the way `split_bucket` needed it.** Prefix
   buckets are inherently skewed (many names share "the"); id-hash buckets
   are close to uniform by construction, so a fixed shard count sized for
   the average case is enough — no oversized-bucket detection/splitting
   logic to port over. The one skew that *does* need handling is
   per-node, not per-shard: see hub capping below.

## What goes in a node's record

Reuse `search_index_export.csv.gz`'s fields as the base (`type`, `id`,
`name`/`title`, `degree`, and the Release-only `artists`/`date` fields
added for disambiguation) and add a capped, typed neighbour list:

```
[type_code, id, name, degree, artists, date, edges]
edges = [[rel_type_code, direction, neighbour_type_code, neighbour_id], ...]
```

Neighbour records carry only enough to draw the next hop and refetch it —
not the neighbour's own name/profile inline, which would duplicate every
node's data once per edge into it. The client already has (or fetches) the
neighbour's own shard record for its display fields; the edge list is
just the adjacency, same division of labour `_expand_two_hop` has today
between "this node's data" and "walk to the next one."

**Hub capping is not optional and is not new engineering** — `server.py`'s
`_neighbours` already solves exactly this problem for the live API (a
Group like Black Sabbath has ~15x more `CREDITED` edges than `MEMBER_OF`
ones, so a flat limit starves structural edges). Port the same
`REL_TYPES`-priority, per-type-budget logic into the export: cap each
node's edge list at build time using the same ordering (`MEMBER_OF`,
`SUBLABEL`, `ALIAS_OF` before `CREDITED`, `RELEASED_ON`) and the same
budget shape as `MAX_LIMIT`. Without this, a hub like "Various" or a major
label would blow its shard's size out — the id-hash bucketing keeps
*shard count* uniform, but a single oversized node inside a shard is a
separate failure mode the search-index work never had to deal with
(a name has no analogous "degree").

**Two-hop is not precomputed.** `_expand_two_hop` does two hops
server-side today purely to save round trips against a live database.
Static files have no per-request server cost, so the client can do it
in two sequential (well, one-then-N-parallel) fetches instead: fetch the
tapped node's own shard, then fetch each first-hop neighbour's shard in
parallel and merge — which is exactly what "look up this id's own
1-hop record" already provides, applied twice. Precomputing 2-hop
adjacency server-side would multiply the corpus by something like average
degree, for a saving (fewer client fetches) that matters when a network
round trip is expensive and doesn't when it's a same-origin/CDN-cached
static file. Not worth the size cost here.

## Sourcing the edges: a bulk streaming export, not one Cypher call per node

`export_search_index.py` streams nodes once. Edges need the analogous
streaming pass, but *per relationship type* — five `MATCH (a)-[r:TYPE]-(b)
RETURN elementId(a), elementId(b)` streams (or their Discogs-id
equivalent, same id choice `export_search_index.py` already made and
justified: native ids survive a reimport, `elementId` doesn't) — not
15M individual per-node lookups, which at any per-query latency above a
few tenths of a millisecond would take hours over Bolt regardless of
indexing. The natural place to accumulate this is the same kind of
SQLite staging table `discogs_to_neo4j.py` already uses for labels: a
`(node_type, node_id) -> edges blob` or plain `(from, from_type, rel,
to, to_type)` table, built by five streaming inserts, then read back
in id-hash order for the shard build's phase 2. This is genuinely new
work — nothing in the repo streams relationships in bulk today, only
`_neighbours`' one-node-at-a-time pattern — but it's the same shape of
problem `sqlite_to_csv.py` already solves (accumulate, then export), not
a new technique.

## Sizing estimate

Order-of-magnitude, to sanity-check this is shippable at all before
building it:

| | |
|---|---|
| Nodes | ~15.16M |
| Relationship rows (sum of the 5 types, per CLAUDE.md's measured counts) | ~19–20M, ~40M directed adjacency entries |
| Per-node base fields | same order as `search_index_export.csv.gz`: ~36 bytes/row uncompressed for `type,id,name,degree` alone: 543 MB / 15.16M rows |
| Per-edge entry, compact JSON (`[code,dir,code,id]`) | ~20–25 bytes |
| **Rough total, uncompressed** | **~1.5–2 GB**, i.e. the same order as the existing `search_index_export.csv.gz` (543 MB) plus the edge list on top |
| Compressed (host gzip/brotli, free per the search-index note) | roughly a third to a half of that |

Never fetched all at once — same as the search shards, a viewer session
touches a handful of shard files per tap, not the corpus — so total
corpus size mostly matters for build time and storage, not any one
user's transfer. **Shard count**: sized the same way `--partitions`/
`--max-shard-rows` were tuned for search (`shard_search_index.py`'s real
run needed its defaults raised once actual skew was measured — expect
the same here), aiming for shards in the tens-of-KB range, i.e. low
thousands of nodes per shard against ~15M nodes → on the order of a few
thousand shard files. Comfortably clear of every problem in the "millions
of files" section above, and clear of Cloudflare Pages' 20,000-file cap
with room to spare.

## What doesn't need to change

- **`web/vendor/`'s graphology + sigma stay exactly as they are.**
  `app.js` already builds the client-side graph with graphology and
  renders with sigma; only the *fetch* layer for expand changes, from
  `/api/expand?id=` to a static-shard lookup. The mass-spring layout,
  drag physics, node-border rendering, hover pill — none of it is
  backend-aware and none of it needs touching.
- **The search half is done.** `web/search-index/` + the `/v2/search`
  harness already resolve a typed query to a seed node id with no
  backend. This work only needs to make *that id* expandable without a
  backend either — the two pieces meet at "here is an id, now draw its
  neighbours," same handoff `app.js`'s `selectSuggestion` → `expandNode`
  already has today, just re-pointed at a static fetch.
- **`_rank_matches`' neighbour-boost gap is already a known, separately
  tracked open problem** (search-relevance note, CLAUDE.md's Known
  Issues) — this work doesn't need to solve it, just not make it worse.

## What's genuinely new / open

1. **The bulk relationship export + staging store** — no existing script
   does this; closest precedent is `sqlite_to_csv.py`'s accumulate-then-
   export shape for labels, and `_neighbours`' per-type-budget capping
   logic, both reusable as *patterns*, not as code to import directly.
2. **A portable id-hash function**, implemented once in Python (build)
   and once in JS (client), that must agree exactly — the one place this
   plan crosses the language boundary the way the search-index work never
   had to (its hash was build-side only).
3. **Access control.** `server.py` currently gates everything behind
   `APP_PASSWORD`. A fully static host has no server to check it — going
   static either means the graph is public, or auth moves to the hosting
   edge (e.g. Cloudflare Access, a hosting provider's basic-auth feature).
   Not a technical blocker, but a decision this plan doesn't make on its
   own — worth raising before committing to a host.
4. **`/api/resolve` (the `[a123456]`/`[l=Name]` profile-link feature)**
   also currently depends on the live database for the free-text
   fallback path (`_rank_matches` over `entitySearch`). The numeric-id
   path (`REF_KIND_LABELS`) is a direct property lookup and maps cleanly
   onto "fetch this id's shard"; the free-text fallback would need to
   route through the search shards instead, same as the live-search box
   does. Not covered by this note beyond flagging it.
5. **Rebuild cadence.** Discogs ships monthly; a full rebuild-and-redeploy
   per month (same cadence the rest of the pipeline already assumes) is
   almost certainly fine — no incremental/delta update mechanism is
   proposed here, and none looks necessary at this scale.

## Feasibility

Most of the hard-won engineering this would need has already been done
once, for search, and the bugs that design went through
(`notes/static-search-downsize-2026-08-19.md`'s 2026-09-10/11 updates —
the filename-vs-URL-encoding split, the single-vs-plural shard fetch,
the Discogs "Not On Label" skew) are exactly the kind that only show up
under a real build against real data, not from reading the code. Expect
the graph-shard build to rediscover a version of at least the "one bucket
way oversized" class of bug (hub nodes, this time, instead of a common
name prefix), since it's the same shape of problem in a new place.

Rough shape of the remaining work, most reusing an existing pattern:

| Piece | Precedent to reuse | New work |
|---|---|---|
| Bulk edge export → SQLite staging | `sqlite_to_csv.py`'s accumulate/export shape | the 5 streaming Cypher queries + staging schema |
| Per-node record assembly, hub capping | `server.py`'s `_neighbours` budget logic | porting it from query-time to build-time |
| Two-phase, flat-memory shard build | `shard_search_index.py` directly | id-hash instead of prefix-hash; a portable hash fn |
| Client expand-by-id + merge | `app.js`'s `expandNode`/`beginNewGraph` merge logic | swap the fetch target; parallel second-hop fetches |
| Standalone test harness before wiring in | `web/v2/search.js` + `search.html` pattern | a `/v2/expand`-shaped equivalent |

Nothing here needs new libraries, a new client-side graph engine, or a
different hosting model than what's already been decided for search.
Given the precedent, this reads as a few focused days of work — export +
staging, shard build, client fetch/merge, then a testing/tuning pass
against the real dump's real skew — rather than a research problem. The
open items above (access control, `/api/resolve`'s free-text path,
picking a host) are decisions to make, not unknowns to solve.
